## 工程是怎么建的（2026-11-09）

1. `.ioc` 从 `Chassis_test.ioc` 改来，和它的区别：
   - 去掉 CAN2：引脚 PB5/PB6、中断、初始化函数都去掉了。
   - CAN1 打开自动重发（`CAN1.NART=ENABLE`），原因见根目录 notes 第 4 节 RS05 那条：RS05 的应答比发给它的帧都优先，不重发的话，同时起步时主机的帧会直接丢。
   - 改了工程名。

   其余和 Chassis_test 一样：HSE 12 MHz → 168 MHz；CAN1 在 PD0/PD1，1 Mbps（分频 3、BS1 9、BS2 4）；开了自动离线恢复（`ABOM`）；RX0 中断优先级 0；只拷用到的库（Drivers 共 76 个文件、6.4 MB）。
2. 用 CubeMX 6.15 命令行生成，做法见 `Chassis_test/notes.md`「工程是怎么建的」。日志里没有 ERROR。生成的 `can.c` 里 `AutoRetransmission = ENABLE`、`AutoBusOff = ENABLE`。
3. main.c 只在 USER CODE 段里加了 `#include "robot.h"`、`Robot_Init()`、`Robot_Loop()`。顶层 CMakeLists.txt 加了 `SHARED_DIR`（`../../../Shared`）和上表那几个文件。
4. CLion 打开 `Test_Module/Gimbal/RS05_test`，照别的工程建「OpenOCD 下载并运行」配置，board config 用 `D:\OpenOCD_Config\DAPLink\stm32f4.cfg`。用 Debug 预设编译，输出 `build/Debug/RS05_test.elf`，脚本默认读这个 ELF。

自动重发的副作用：电机没上电时没人应答，邮箱里的帧会一直重发，3 个邮箱很快占满，`RS05_Manager_SendAll` 返回 `HAL_BUSY`。电机上电后会自己恢复。

## 程序做什么

- **每 1 ms 一帧电机帧**（驱动的 `RS05_Manager_SendAll`）：
  - `rs05_test_enable = 0` 时发停止帧（类型 4）：电机进 Reset、没力，照样回类型 2 反馈。
  - `= 1` 时，电机没在运行就先走使能序列（run_mode = 3 → canTimeout = 100 ms → iq_ref = 0 → 使能，约 4 ms）；运行以后每 1 ms 写一次 iq_ref。
  - 电流先限到 ±1 A（`RS05_TEST_CURRENT_LIMIT_A`，约 0.67 N·m）。
  - 输出轴超过 6 rad/s（`RS05_TEST_SPEED_LIMIT_RAD_S`，约 1 圈/秒）就给 0，降下来再给。电流模式没有速度环，不这样做的话，空载会一直加速到约 50 rad/s。
  - 实际发出去的电流看 `rs05_motor.current_a`。
- **每 10 ms 用类型 17 读一个参数**，7 个参数轮流读，所以每个约 70 ms 更新一次。
  - 应答在接收中断里按 index 填进 `rs05_test_params`：Byte4~7 原样存进 `raw`，读成功、读失败分别计数。
  - 读那一帧没进邮箱时，下次再读同一个。
- **过滤器**：什么帧都收。组 3 收全部标准数据帧，组 4 收全部扩展数据帧（类型 17 的应答也从这里进来），组 1 是驱动配的、只收类型 2。
- **接收回调**每次读一帧：先交给驱动（只认类型 2），再交给读参数（只认类型 17、DLC 8），最后记进收帧记录。
- **收帧记录**（`rs05_test_rx_log`，16 帧环形，`rs05_test_rx_count` 是记过的总数）：现在这个电机的类型 2、17 已经被驱动和读参数用掉，不记，免得 1 kHz 的反馈把别的帧冲掉；其余的都记。每帧 16 字节：id（bit31 为 1 是扩展帧）、dlc、data[8]。
- **发任意一帧**（`rs05_test_tx_frame` + `rs05_test_tx_pending`）：外面先填好帧，再把 pending 置 1，程序在下一个 1 ms 里发出去，发进邮箱后清 0；标准帧 ID 超过 0x7FF 或 DLC 超过 8 时改成 2，什么都不发。排在电机帧、读参数后面，邮箱满了就下次再发。
- **电机 ID 只存一份**：在 `rs05_motor.id`（上电时是 `RS05_TEST_MOTOR_ID` = 1）。驱动发电机帧、读参数、认应答都看它，所以运行中改了它，三样一起换过去，不用重新烧。
- 原来固件里的 ID 扫描（`rs05_test_scan`、`rs05_test_found`）去掉了，改成脚本用"发任意一帧 + 收帧记录"来扫，这样 MIT、CANopen 也能试。

### 读哪些参数

| index | 名字 | 类型 | 手册里在哪 | 用来看什么 |
|---|---|---|---|---|
| 0x7019 | mechPos | float，rad | 4.1 节最后的参数列表：负载端计圈机械角度 | 和类型 2 的 `position_rad` 对照（是不是一回事还没确认） |
| 0x701A | iqf | float，A | 同上：iq 滤波值 | 电流方向：应该和给的电流同号 |
| 0x7029 | zero_sta | uint8 | 同上 | 0：上电读数在 0~2π；1：在 −π~π |
| 0x3004 | encoderRaw | int16 | 3.3.4 节上位机参数表：磁编码器采样值（示例 11396） | 编码器装在哪：输出轴转一圈，它绕几次 |
| 0x3015 | modPos | float，rad | 同上：电机未计圈机械角度（示例 4.363409） | 同上 |
| 0x3014 | rotation | int16 | 同上：圈数（示例 1） | 同上；上电时是多少 |
| 0x2005 | MechOffset | float | 同上：磁编码器角度偏置（示例 4.619583） | 核对 mechPos 的公式（下面第三条） |

- 类型 17 能读的，手册 4.1 节只列了 0x70xx。0x20xx、0x30xx 是上位机参数表里的，类型 17 能不能读手册没写，这次正好试一下：`ok_count` 在涨就是能读；`fail_count` 在涨是电机回了"读取失败"；两个都是 0 说明电机没回。
- 手册示例里 11396 / 16384 × 2π = 4.370，和 modPos 的 4.363 很接近（示例里的数可能不是同一时刻读的）。所以 encoderRaw 应该就是 14 bit 编码器的读数，modPos 是同一个角度换成 rad。
- 手册示例满足 mechPos = (rotation × 2π + modPos − MechOffset) / 7.75：(1 × 2π + 4.363409 − 4.619583) / 7.75 = 0.777679，和示例的 mechPos 一样（根目录 notes 第 5 节）。
- 要加别的参数：robot.c 的 `rs05_test_params` 加一行 index；脚本的 `PARAMS` 加一行名字和类型。脚本里不加也行，会按原始值显示。

## 怎么读写（OpenOCD 不停核）

脚本路径要写全（2026-11-09 第一次用时在 `C:\Windows\System32` 下运行，相对路径找不到文件）。在哪个目录下运行都行：

```bash
python C:/Project/RM_Infantry/Test_Module/Gimbal/RS05_test/tools/rs05_watch.py
```

后面的参数加在这一行最后：

| 加的参数 | 作用 |
|---|---|
| （不加） | 一直读，每 0.2 s 一行，Ctrl+C 退出 |
| `--once` | 读一次，打全部字段：参数表带成功 / 失败次数和原始值、最近收到的帧；没收到反馈时按 TEC / LEC 给出该查什么 |
| `set enable 1` | 0 停止（没力），1 电流模式 |
| `set current 0.1` | A，程序里限到 ±1 A |
| `set id 127` | 把程序用的电机 ID 改成 127，不用重新烧（复位后回到 1） |
| `scan` | 依次试三种协议，各给 ID 1~127 发一帧（私有协议从 0 开始），哪种先有回话就停，打出电机在哪种协议、ID 多少、下一步做什么。几秒到十几秒 |
| `log` | 一直打印新收到的帧（驱动、读参数用掉的除外），每帧后面写上猜它是什么；Ctrl+C 退出 |
| `send std 0x7F FF FF FF FF FF FF FF FD` | 发一帧：`std` / `ext`、ID、0~8 个十六进制字节；再打印 0.2 s 内收到的帧 |

`scan` 每种协议发的帧（都是只读或无害的）：

| 协议 | 发什么 | 认什么样的应答 |
|---|---|---|
| 私有 | 类型 17 读 mechPos（扩展帧 0x1100FD00 + ID） | 任意电机 ID 的类型 17 应答 |
| MIT | 指令 2「停止」（标准帧，ID 就是电机 ID，`FF FF FF FF FF FF FF FD`），电机进 Reset、没力 | 标准帧、8 字节、data[0] 正好是刚问过的 ID（应答发给主机 ID，默认 0xFD） |
| CANopen | SDO 读 0x1000（标准帧 0x600 + 节点号，`40 00 10 00 00 00 00 00`） | 0x580 + 节点号。前两种都没回才发 |

找到以后会打出下一步：私有协议就 `set id`；MIT、CANopen 就打出切回私有协议要发的那一帧（手册第 6 章指令 8 / 5.10 节）。这一帧会写进电机，断电再上电才生效，所以脚本只打印、不自己发。

scan 开始先看驱动：现在这个 ID（`rs05_motor.id`）100 ms 内收到过类型 2，就直接报"私有协议，正常"，只再扫一遍私有协议找别的电机。原因：这个 ID 的类型 2、17 被驱动和读参数直接用掉，不进收帧记录，后面几轮看不见它（2026-11-09 踩过：电机已经好了，scan 却说没人回话）。

- 脚本先连 127.0.0.1:6666（OpenOCD 的 TCL 端口），连不上就自己起一个 OpenOCD。用的是 `D:\DevEnv\DevEnv\DevEnv\openocd-v0.12.0-i686-w64-mingw32\bin\openocd.exe` 和上面那个 board config，只开 TCL 端口。只连，不复位、不停核。
- 自己起的 OpenOCD 单独放在一个进程组里：按 Ctrl+C 只打断脚本，由脚本发 `shutdown` 让 OpenOCD 正常退出。第一次上板时还没这样做，OpenOCD 被半路打断，DAPLink 里留下没收的应答，下一次连就报 `CMSIS-DAP command mismatch`。现在脚本遇到这个错误会自动再连一次（第一次已经把旧应答收掉了）；还不行就拔插 DAPLink。
- 变量地址每次都用 `arm-none-eabi-nm` 从 ELF 里查。开头先核对参数表的 7 个 index，对不上就退出，什么都不写。ELF 不在 `build/Debug` 时用 `--elf` 指定。
- 一行里各列的意思：
  - `tick`：HAL 毫秒数。
  - `id`：程序现在用的电机 ID（`rs05_motor.id`）。
  - `fb`：最后一帧反馈是几毫秒前收到的，`--` 表示还没收到过。
  - `st`：0 Reset、1 标定、2 运行。
  - `flt`：故障位，bit0 欠压、1 三相电流、2 过温、3 磁编码、4 堵转过载、5 未标定。
  - `en`、`cmd_A`：写进去的指令；`out_A`：限流、限速以后实际发的。
  - 参数列：`--` 表示电机没回过，`fail` 表示只回过"读取失败"。
  - `TEC`、`REC`、`LEC`：CAN1 的错误计数和最近一次错误类型。

2026-11-09 改成"什么帧都收"以后这次 Debug 编译的地址如下。重新编译后可能会变，以 `arm-none-eabi-nm` 为准：

| 变量 | 地址 | 类型 / 字段偏移 |
|---|---|---|
| `rs05_test_enable` | 0x200000F4 | uint8，写 |
| `rs05_test_current_a` | 0x200000F8 | float，写 |
| `rs05_test_rx_log` | 0x200000FC | 16 × 16 B，每帧：+0 id（bit31 为 1 是扩展帧）、+4 dlc、+5 data[8] |
| `rs05_test_rx_count` | 0x200001FC | uint32，记过的帧数；最新一帧在 `rx_log[(count − 1) % 16]` |
| `rs05_test_tx_frame` | 0x20000200 | 16 B，格式同上，写 |
| `rs05_test_tx_pending` | 0x20000210 | uint8：写 1 发上面那一帧，发进邮箱后程序清 0，不合法时变 2 |
| `rs05_motor` | 0x200000D8 | `RS05_Motor_t`，28 B：+0 id（u8，可以改）、+4 current_a、+12 position_rad、+16 velocity_rad_s、+20 state（u8）、+21 fault（u8）、+24 feedback_tick |
| `rs05_test_params` | 0x2000000C | 7 × 16 B，每项：+0 index（u16）、+4 raw、+8 ok_count、+12 fail_count |
| `uwTick` | 0x20000098 | uint32 |
| `CAN1->ESR` | 0x40006418 | bit2 BOFF、bit6~4 LEC、bit23~16 TEC、bit31~24 REC |

不用脚本时，也可以在 OpenOCD 的 telnet（4444）里直接读写，例如 `mdw 0x200000d8 7`、`mwb 0x200000f4 1`、`mww 0x200000f8 0x3DCCCCCD`。float 要自己换成十六进制：0.05 = 0x3D4CCCCD，0.1 = 0x3DCCCCCD，−0.1 = 0xBDCCCCCD，0.2 = 0x3E4CCCCD，−0.2 = 0xBE4CCCCD，0 = 0。

## 上板步骤（第 2 步卡住了，见「上板记录」）

0. **设电机。** 用上位机（RobStride 调试软件 + USB-CAN）把电机 CAN ID 设成 1（和 robot.c 的 `RS05_TEST_MOTOR_ID` 一样），私有协议，1 Mbps。`zero_sta` 不用改，它只影响上电读数的范围，这次程序会把它读出来。没有上位机时，先跳过这一步，第 2 步用 `scan` 找。
1. **接线。**
   - RS05 的 XT30(2+2) 接 24 V（15~60 V 可用）。CANH、CANL 接 C 板 CAN1 的 2-pin 口：1 脚 CANL、2 脚 CANH。
   - C 板也要接 24 V 或插 USB：只接 DAPLink 时，CAN 收发器没有 5 V（根目录 notes 第 5 节）。
   - 终端电阻：手册没说电机里有没有。断电量 CANH–CANL：只有 C 板那个 120 Ω 时读 120 Ω（线短能用），两头都有时约 60 Ω。
2. **烧录，开始读。**
   - CLion 烧录。烧完确认 CLion 的 OpenOCD 已经退出（调试会话要停掉），再运行脚本（路径写全，见「怎么读写」）。
   - 正常的样子：`tick` 在涨，`fb` 是 0~1，`st` 0，`flt` 00，TEC、REC 都是 0，7 个参数列有数或者显示 `fail`。
   - RS05 和 C 板一起上电时，约 1.4 s 内不回话（果园工程实测），这段时间 `fb` 是 `--`。
   - `fb` 一直是 `--`：先跑一次 `--once`，最后一行的提示按 CAN 的错误状态分三种：
     - TEC 大、LEC 是位错误、或者 BUS-OFF：帧发不出去。查 C 板有没有 24 V 或 USB（只接 DAPLink 时收发器没有 5 V）、CAN 线。
     - LEC 是"没有应答"、TEC 在 128 左右：总线上没有别人。查电机有没有电、CANH / CANL 有没有接反。
     - TEC、LEC 都是 0：帧发出去了、有人应答，就是电机不回话。跑 `scan`，照它最后打出的下一步做：
       - 私有协议、ID 不是 1：`set id <那个 ID>`，`fb` 应该马上变成 0~1。以后都用这个 ID 的话，改 robot.c 的 `RS05_TEST_MOTOR_ID`（不改的话复位后回到 1）。
       - MIT 或 CANopen：发它打出来的那一帧（切回私有协议，会写进电机），给电机断电再上电，再 `scan`。
       - 三种协议都没回：开着 `log`，给电机断电再上电，看有没有帧；再查 CAN1 上还接了什么（应答的可能不是 RS05）。
3. **第一步：手转。** 保持 `rs05_test_enable = 0`，电机没力。
   - 慢慢转输出轴，看 `pos_rad`，转一圈应该变约 6.28。记下从输出轴端看，往哪个方向转时它变大。
   - 往一个方向转两圈以上：手册 4.2.3 节说类型 2 的角度在 −4π~4π（±12.57）之间循环，看越界时怎么跳。
   - 停下来对照 `mechPos`：两个数相同、差 2π 的整数倍，还是别的关系？记下来。
4. **第二步：电流方向。**
   - 先捏住输出轴，或者确认轴上什么都没装。`set enable 1`：几毫秒内 `st` 变成 2，这时电流是 0，还是没力。
   - `set current 0.1`（约 0.07 N·m，按额定 1.6 N·m / 2.4 A 估的）：感觉它往哪边推。`iqf` 应接近 +0.1。

## 容易错的

1. DAPLink 同时只能给一个 OpenOCD 用。脚本开着时，CLion 烧不了程序，先 Ctrl+C。CLion 的调试会话开着时，脚本起不了自己的 OpenOCD。
2. 重新编译后地址可能会变。脚本每次都从 ELF 里查，所以 ELF 必须和板子里的程序一致；对不上时脚本会报错退出。
3. 改了 `RS05_Motor_t`（rs05.h）、`TestParam_t` 或 `TestFrame_t`（robot.c）的字段，脚本里的 `MOTOR_FORMAT`、`PARAM_FORMAT`、`FRAME_FORMAT` 要跟着改。
4. 电流模式没有速度环，空载给电流会一直加速；程序把速度限在 6 rad/s 附近。轴上装了东西的话，先固定好。
5. canTimeout 设的是 100 ms：在 CLion 里停在断点超过 100 ms，电机会自己进 Reset、没力；继续运行后，驱动几毫秒内会重新使能。OpenOCD 不停核读写不受影响。
6. OpenOCD 0.12.0 只有 target 下的 `read_memory` / `write_memory`（`stm32f4x.cpu read_memory …`），没有全局命令，所以脚本里写的是 `[target current] read_memory`。
7. OpenOCD 报 `CMSIS-DAP command mismatch. Sent 0x0 received 0x5`：上一个 OpenOCD 在传输中途被打断，DAPLink 里留了一个 DAP_Transfer（0x05）的应答没收。再连一次一般就好，脚本会自动再连一次；还不行就拔插 DAPLink。
8. TEC、LEC 都是 0 不代表电机在：只说明有节点给 C 板的帧应答了。应答是 CAN 控制器硬件做的，和电机 ID、协议都无关：电机 ID 不对、或者在 MIT / CANopen 协议时，它照样应答，只是不回话。
9. MIT 的应答发给主机 ID，默认是标准帧 0x0FD，正好也在 CANopen 紧急报文的范围（0x081~0x0FF）里，光看 ID 分不出来。所以 `scan` 不靠猜 ID：MIT 那一轮只认 data[0] 正好是刚问过的电机 ID 的 8 字节标准帧，CANopen 那一轮只认 0x580 + 节点号。
10. MIT 的「停止」是 `FF FF FF FF FF FF FF FD`，「切回私有协议」（指令 8）是 `FF FF FF FF FF FF 00 FD`，只差倒数第二个字节。后者会写进电机，断电再上电生效，手打时别弄混。

## 主机检查（2026-11-09；测试代码在 `%TEMP%\rs05_test_host`，没进仓库）

编的是 robot.c 原文件（直接 include 进测试，好看到 static 变量），再加 rs05.c、can_bus.c、user_math.c 原文件和一个假 HAL。用 CLion 自带的 MinGW gcc 编译，`-Wall -Wextra -Wconversion -Wshadow` 没有警告。改成"什么帧都收"以后 486 项全过（第一版 411 项）：

- **初始化**：
  - 三个过滤器，都是 32 位掩码、进 FIFO0、`SlaveStartFilterBank` 14：组 3 收全部标准数据帧（ID 0000 0000，掩码 0000 0006），组 4 收全部扩展数据帧（ID 0000 0004，掩码 0000 0006），组 1 是驱动的类型 2（ID 1000 0004，掩码 F800 0006）。
  - CAN 只启动一次，接收中断只开一次。
  - 按 bxCAN 32 位掩码的规则算过：组 3 收 0x000、0x0FD、0x7FF，不收扩展帧、远程帧；组 4 收类型 0、类型 17、0x1FFFFFFF，不收标准帧、远程帧；组 1 不收类型 17。
- **不出力**：每 1 ms 一帧停止帧（0x0400FD01）。每 10 ms 多一帧读参数（0x1100FD01，数据 19 70 00 00 00 00 00 00），7 个 index 按表的顺序轮流。
- **邮箱不够**：读参数那一拍只剩一个邮箱时，电机帧先进去；读参数那帧没进，下次读同一个 index。
- **应答**：
  - 读成功：存进 raw（float 1.5 → 0x3FC00000、int16 11396、uint8 1），ok_count 加 1。
  - 读失败：只加 fail_count，不改 raw。
  - 别的电机 ID、表里没有的 index、DLC 不是 8、远程帧、标准帧，都不改数据；类型 2 只交给驱动。
  - 手册 4.1 节读取示例的数据字节（00 00 F0 41）按同样的字节序解出来是 30.0。
- **出力**（state 2）：发的是 iq_ref。给 0.3 发 0.3，给 5 发 1，给 −5 发 −1。速度 ±6.5 rad/s 时，不管电流正负都发 0；5.9 rad/s 时照常发。电机没在运行时，从写 run_mode = 3 开始；enable 改回 0 后发停止帧。
- **收帧记录**：MIT 样子的标准帧 0x0FD、别的电机的类型 2、类型 0 应答、CANopen 开机帧（DLC 1）都记进去，扩展帧的 id 带 bit31；现在这个电机的类型 2、17 不记，但驱动和读参数照样用上了。再来 20 帧以后，最新一帧在 `(count − 1) % 16`，最老的是 16 帧以前那一帧。
- **发任意一帧**：MIT「停止」标准帧 0x7F 原样发出、pending 清 0、只发一次；扩展帧 0x1100FD05 按扩展帧发；邮箱只剩一个时电机帧先进去、这一帧下次再发；标准帧 ID 0x800、DLC 9 时 pending 变 2，什么都不发。
- **在线改 ID**：`rs05_motor.id` 改成 0x7F 后，停止帧变成 0x0400FD7F，读参数变成 0x1100FD7F，没有再发给 ID 1 的帧；ID 0x7F 的类型 17、类型 2 应答被用上，ID 1 的不再用。
- **故意改坏 15 处**，每处都有检查失败：收帧记录也记了自己电机的帧；扩展帧没带 bit31；DLC 没存；计数不涨；发完不清 pending；不合法时不置 2；扩展帧当标准帧发；标准帧 ID 不查范围；标准帧过滤器写成扩展帧的；不配扩展帧过滤器；读成功 / 失败的判断反了；认应答用固定的 ID 1；读参数用固定的 ID 1；去掉限速；去掉限流。
